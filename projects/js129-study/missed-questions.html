Problem 2: Replacing Dog.prototype without restoring constructor

Code

'use strict';
```

function Dog(name) {
this.name = name;
}

Dog.prototype = {
bark() {
console.log(`${this.name} barks.`);
}
};

let dog = new Dog('Rex');

console.log(Dog.prototype.hasOwnProperty('constructor'));
console.log(dog.constructor === Dog);
console.log(dog.constructor === Object);
```

My answer

Dog.prototype.hasOwnProperty('constructor') // false
```

dog.constructor === Dog                    // true / unsure
dog.constructor === Object                 // unsure
```

Correct answer

false
```

false
true
```

What was wrong: I treated dog.constructor as if it automatically remembered that dog was created by Dog.

But dog.constructor is not a hidden record of which constructor function created the object. It is just a normal property lookup for a property named constructor.

Normally, a constructor function starts with a default prototype object that has a constructor property:

Dog.prototype.constructor === Dog;

But when I replace the prototype with an object literal:

Dog.prototype = {
```

bark() {
console.log(`${this.name} barks.`);
}
};
```

I throw away the original default prototype object. The new object has bark, but it does not have its own constructor property.

The prototype chain is:

dog -> Dog.prototype -> Object.prototype -> null

So when JavaScript evaluates dog.constructor, it searches like this:

dog.hasOwnProperty('constructor')              // false
```

Dog.prototype.hasOwnProperty('constructor')    // false
Object.prototype.hasOwnProperty('constructor') // true
```

Object.prototype.constructor points to Object, so:

dog.constructor === Dog    // false
```

dog.constructor === Object // true
```

Rule: constructor is just a property. Replacing a prototype object can remove the default constructor property unless I manually restore it.

Problem 7: Class method vs method assigned inside the constructor

Code

'use strict';
```

class Dog {
constructor(name) {
this.name = name;
this.bark = function() {
console.log(`${this.name} barks.`);
};
}
}

let dog1 = new Dog('Rex');
let dog2 = new Dog('Maya');

console.log(dog1.hasOwnProperty('bark'));
console.log(Dog.prototype.hasOwnProperty('bark'));
console.log(dog1.bark === dog2.bark);
```

Correct answer

true
```

false
false
```

What was shaky: I needed to be more precise about whether bark was on the instance or on Dog.prototype.

These two patterns are very different:

class Dog {
```

bark() {}
}
```

versus:

class Dog {
```

constructor() {
this.bark = function() {};
}
}
```

This form:

bark() {}

puts the method on Dog.prototype. Every dog shares the same method.

But this form:

this.bark = function() {};

runs inside the constructor every time a new dog is created. It creates a new function object and assigns it directly to that specific instance.

So with:

let dog1 = new Dog('Rex');
```

let dog2 = new Dog('Maya');
```

the structure is:

dog1 owns name
```

dog1 owns bark

dog2 owns name
dog2 owns bark

Dog.prototype does not own bark
```

That is why:

dog1.hasOwnProperty('bark')          // true
```

Dog.prototype.hasOwnProperty('bark') // false
dog1.bark === dog2.bark              // false
```

Rule:

this.bark = function() {}; // instance owns bark
```

bark() {}                  // Dog.prototype owns bark

static bark() {}           // Dog owns bark
```

Problem 8: Private field plus getter nuance

Code

'use strict';
```

class Dog {
#name;

constructor(name) {
this.#name = name;
}

get name() {
return this.#name;
}

rename(newName) {
this.#name = newName;
}
}

let dog = new Dog('Rex');

console.log(dog.name);
console.log(dog.hasOwnProperty('name'));
console.log(dog.hasOwnProperty('rename'));
console.log(Dog.prototype.hasOwnProperty('rename'));

dog.rename('Maya');
console.log(dog.name);
```

Correct answer

Rex
```

false
false
true
Maya
```

What needed correction: The phrase “the dog has name” can be misleading here.

This class has a private field:

#name

That private field is internal class state. It is not the same thing as a public own property called name.

This works:

dog.name

because the class defines a getter:

get name() {
```

return this.#name;
}
```

The getter lives on Dog.prototype. So the lookup is roughly:

Does dog have an own public property named "name"? No.
```

Does Dog.prototype have a getter named "name"? Yes.
Run the getter with this = dog.
Return dog.#name.
```

That is why both of these can be true:

dog.name                  // "Rex"
```

dog.hasOwnProperty('name') // false
```

Rule: A property access working does not automatically mean the instance owns that property. It may be found through the prototype chain, or it may be a getter.

Problem 12b: Extracting super.speak into a variable

Code

'use strict';
```

class Animal {
speak() {
console.log(`${this.name} makes a noise.`);
}
}

class Dog extends Animal {
constructor(name) {
super();
this.name = name;
}

speak() {
let parentSpeak = super.speak;
parentSpeak();
console.log(`${this.name} barks.`);
}
}

let dog = new Dog('Rex');

dog.speak();
```

My answer

// super does not fix lost this

Correct answer

TypeError

The second log never runs.

This line:

let parentSpeak = super.speak;

gets the parent method from Animal.prototype. Conceptually:

let parentSpeak = Animal.prototype.speak;

But once the method is stored in a variable, the receiver is gone.

Then this line:

parentSpeak();

is a plain function call. There is no object before the dot. In strict mode:

this = undefined

So inside Animal.prototype.speak, this line throws:

console.log(`${this.name} makes a noise.`);

because this is undefined.

Rule: super.speak() preserves the current this. But extracting super.speak into a variable loses the receiver.

Problem 13: Extracting dog.speak when the method contains super

Code

'use strict';
```

class Animal {
speak() {
console.log(`${this.name} makes a noise.`);
}
}

class Dog extends Animal {
constructor(name) {
super();
this.name = name;
}

speak() {
super.speak();
}
}

let dog = new Dog('Rex');

let speak = dog.speak;
speak();
```

My answer

// don't understand this one

Correct answer

TypeError

The confusing part is that super.speak() feels like it should somehow know that the method came from dog. It does not.

This line:

let speak = dog.speak;

copies the function value. It does not copy the receiver.

So this:

speak();

is not the same as:

dog.speak();

This call:

dog.speak();

sets:

this = dog

But this call:

speak();

sets, in strict mode:

this = undefined

So when Dog.prototype.speak starts running, this is already undefined.

Then super.speak() can still find Animal.prototype.speak, but it keeps the same current this. Since the current this is undefined, the parent method also receives undefined.

Assessment phrase: super.speak() finds Animal.prototype.speak, but it does not fix a lost this. Since dog.speak was extracted and called as speak(), this is undefined, so the parent method throws.

Final Problem: constructor vs instanceof after restoring constructor

Code

'use strict';
```

function Animal(name) {
this.name = name;
}

function Dog(name) {
Animal.call(this, name);
}

Dog.prototype = Object.create(Animal.prototype);

let dog = new Dog('Rex');

console.log(dog.constructor === Dog);
console.log(dog.constructor === Animal);
console.log(dog instanceof Dog);
console.log(dog instanceof Animal);

Dog.prototype.constructor = Dog;

console.log(dog.constructor === Dog);
console.log(dog.constructor === Animal);
console.log(dog instanceof Dog);
console.log(dog instanceof Animal);
```

My answer

false
```

true
true
true

true
false
true
false
```

Correct answer

false
```

true
true
true

true
false
true
true
```

What was wrong: The final line should be true, not false.

This line:

Dog.prototype = Object.create(Animal.prototype);

sets up this prototype chain:

dog -> Dog.prototype -> Animal.prototype -> Object.prototype -> null

Before restoring constructor, Dog.prototype does not have its own constructor property. So dog.constructor searches like this:

dog has own constructor? No.
```

Dog.prototype has own constructor? No.
Animal.prototype has own constructor? Yes.
```

So before the restoration:

dog.constructor === Dog      // false
```

dog.constructor === Animal   // true
dog instanceof Dog           // true
dog instanceof Animal        // true
```

Then we do:

Dog.prototype.constructor = Dog;

Now Dog.prototype has its own constructor property. So dog.constructor now finds Dog before it reaches Animal.prototype.

dog.constructor === Dog      // true
```

dog.constructor === Animal   // false
```

But this assignment did not change the prototype chain. The chain is still:

dog -> Dog.prototype -> Animal.prototype -> Object.prototype -> null

Since Animal.prototype is still in the chain:

dog instanceof Animal // true

Rule: Changing Dog.prototype.constructor changes a property. It does not remove Animal.prototype from the prototype chain.

Big Patterns Across the Misses

1. constructor is mostly just a property lookup

dog.constructor

This means: find a property named constructor on dog or its prototype chain.

2. instanceof checks the prototype chain, not the constructor property

dog instanceof Dog

This means: is Dog.prototype anywhere in dog's prototype chain?

3. super finds the parent method, but keeps the current this

super.speak()

This means: find the parent version of speak and call it with the current this. If the current this is already lost, super does not restore it.

4. hasOwnProperty only checks the object itself

dog.hasOwnProperty('bark')

This asks whether dog directly owns bark. It does not matter whether dog.bark() works through the prototype chain.

5. Method placement matters

this.method = function() {}; // instance owns it
```

method() {}                  // prototype owns it

static method() {}           // class / constructor owns it
```

Main takeaway: Most of the mistakes came from treating constructor, super, or instanceof as more magical than they are. The correct approach is to reduce each one to the mechanical rule: property lookup, prototype-chain check, or current-this method call.
